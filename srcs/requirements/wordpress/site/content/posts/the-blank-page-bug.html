The stack booted green. Healthchecks passed, TLS handshook, WordPress installed itself — and the front page served zero bytes with a straight face and an HTTP 200.

[cmd]docker exec wordpress wp --allow-root theme list[/cmd] [out]name status update version (empty)[/out]

The trap: Docker volume copy-up

The image pre-downloaded WordPress with --skip-content — no themes, to save build bytes. The plan was to fetch themes on first boot. But when Docker mounts an empty named volume over a directory that has content in the image, it copies that content into the volume first. So the entrypoint's “is core already there?” check found the theme-less core, took its already cached branch, and its fallback download silently failed behind an || true.

Result: a fully installed WordPress with no theme at all. WordPress renders that as… nothing. A 200 with an empty body — the kind of bug a healthcheck will never catch, because everything is technically running.

The fix: stop depending on copy-up at all

The full core — themes included — is now staged in the image at /usr/src/wordpress, and first boot does one deterministic thing:

[cmd]cp -a /usr/src/wordpress/. /var/www/html/[/cmd]

Zero network at boot, identical behaviour whether copy-up happened or not, and the test suite gained a regression check: an active theme must exist, and the front page must be a real page, not an empty 200.

[callout type="ok" title="lesson"]Never let first-boot correctness depend on Docker's volume copy-up semantics — and never trust an HTTP 200 without checking the body.[/callout]
