Ten containers, one Compose file, one network. The rules below are the reason the stack starts the same way every time, and they are all checked by the test suite rather than trusted.

Built, not pulled

Every image has its own Dockerfile, and every Dockerfile starts FROM alpine:3.23.7. No image comes ready-made from a registry and no tag says latest, so a build today and a build next month start from the same base. Images carry only what they run: there is no database client in the WordPress image, and the MariaDB image drops more than 100 MB of binaries it never uses.

One daemon, as PID 1

Each container runs one service, started through an entrypoint script that follows the same four steps:

  1. Fail fast: set -eu, every required variable checked, every secret file checked non-empty.
  2. Initialise once: the first-boot work runs behind a guard, and the guard is written only after it succeeded, so a boot killed half-way simply starts over.
  3. Wait with a limit: WordPress waits for MariaDB for 60 seconds at most, then exits and lets the restart policy try again. No tail -f, no sleep infinity, no endless loop.
  4. exec the daemon: it becomes PID 1, receives docker stop's signal itself, and no shell is left in front of it.

An arrow reads "is healthy before". Every service has a healthcheck, and depends_on waits for service_healthy, not for a container that has merely started. With checks polled twice a second during start-up, the whole stack goes from docker compose up on empty volumes to a live HTTPS WordPress in about seven seconds (the journal post Seven-second boots has the measurement).

Data in volumes, passwords in files

The database and the WordPress files live in named volumes whose data sits in /home/dlesieur/data; no service bind-mounts a host path. They survive make down, make up and reboots. Passwords never travel as environment variables: they are Docker secrets, mounted as files in /run/secrets and readable by root only, so docker inspect shows none of them.

[callout type="info" title="the mindset"]Each rule removes a way for the stack to behave differently from one start to the next. The same Dockerfile, the same order, the same files: the defense is a demonstration, not a hope.[/callout]
