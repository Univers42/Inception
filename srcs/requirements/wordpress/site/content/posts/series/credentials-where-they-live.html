A credential in the repository is an automatic failure at 42, and the test suite searches every tracked file and the whole git history for one. So each password here is generated, kept outside git, and moved in ways that leave no copy behind.

From the host to a container

Inception's make setup creates secrets/ once, with random passwords, and never overwrites it. The folder is ignored by git. Compose hands each file to the containers that need it as a Docker secret, and the entrypoints read them from /run/secrets.

The administrator's account

The account a person signs in with is not random: it lives on the host, in born2root's secrets file (~/.config/born2root/b2b-secrets, mode 600, outside any repository), as INCEPTION_ADMIN_EMAIL and INCEPTION_ADMIN_PASSWORD. make inception sends both to the guest on ssh's standard input, where no process list can show them, and writes them into secrets/credentials.txt and srcs/.env. On every boot, the WordPress entrypoint checks that the accounts' passwords and the administrator's email match those files, and corrects any that do not. Changing the password is editing one file and redeploying.

What guards the sign-in page

  • A failed sign-in says only that it failed, never whether the account exists.
  • Anonymous visitors cannot list accounts: the REST users route, ?author= and author pages are closed to them, and bylines show a role, not a login name.
  • No password reset by mail: the stack has no mail server, and the secrets file is the reset.
  • nginx limits sign-in attempts to 10 a minute per address, and refuses XML-RPC outright.
  • wp-admin has no theme or plugin editor (DISALLOW_FILE_EDIT): code changes go through the repository, never through a browser.
[callout type="warn" title="one key stays out"]The certification authority's private key never enters a container. Browsers trust that CA, so a container that held its key could impersonate any website to them.[/callout]
