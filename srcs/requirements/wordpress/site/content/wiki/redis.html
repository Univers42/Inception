Three parts have to line up, and it is the third that is usually missed:

  1. php84-pecl-redis in the WordPress image (the PHP extension).
  2. WP_REDIS_HOST, WP_REDIS_PORT, WP_CACHE_KEY_SALT and WP_CACHE in wp-config.php. The salt is the domain, so two installs sharing a Redis instance cannot read each other's keys.
  3. The drop-in. wp redis enable writes wp-content/object-cache.php. Without it the plugin is installed, active, and caching nothing.

The entrypoint does all three, non-fatally — the site must boot even if Redis is unreachable, because a cache is an optimisation, not a dependency. It also patches an existing wp-config.php: the config heredoc only runs on a first install, and the site volume outlives image rebuilds.

Redis is configured as a cache, not a database — save "", appendonly no, maxmemory 256mb, maxmemory-policy allkeys-lru. Without an eviction policy Redis answers writes with an error once full, which WordPress would surface as a broken page rather than a cache miss.
