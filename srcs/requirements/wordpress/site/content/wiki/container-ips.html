fastcgi_pass uses a variable plus an explicit resolver 127.0.0.11:

resolver               127.0.0.11 valid=10s ipv6=off;
set $upstream_wordpress wordpress:9000;
fastcgi_pass            $upstream_wordpress;

With a literal fastcgi_pass wordpress:9000; nginx resolves the name once when it loads its config and caches that address for the life of the process. Recreate the wordpress container — a rebuild, a crash, any docker compose up -d wordpress — and it returns on a new IP while nginx keeps dialling the old one, answering 502 on every request until nginx itself is restarted. Putting the upstream in a variable forces re-resolution per request. Verified by moving wordpress from 172.18.0.9 to 172.18.0.10 without touching nginx: the site stayed at 200.

The lab's /lab/ and /api/v1/ locations get the same re-resolution from an upstream block with server … resolve, which also keeps connections alive; a variable cannot (§13.1).
