One door, three rooms

[arch]

Every request enters through nginx on port 443 — TLS 1.2/1.3 is terminated there, static assets are served straight from the shared read-only volume, and only .php requests travel deeper over FastCGI. WordPress runs php-fpm 8.4 workers as nobody; MariaDB 11.4 answers on the internal network only. Neither app container is reachable from the host.

The bridge network

A single user-defined bridge network, inception, connects the three containers. Docker's embedded DNS resolves service names — nginx forwards to wordpress:9000, WordPress connects to mariadb:3306. network_mode: host and links: are forbidden by the subject and absent; the suite verifies both.

Named volumes at a fixed host path

Two top-level named volumes satisfy both subject rules at once — they are real named volumes (services never bind-mount host paths), and their data lives inside /home/dlesieur/data via the local driver's device option:

inception_db_data/home/dlesieur/data/mariadbMariaDB data directory

Secrets, not environment variables

Compose mounts each credential file at /run/secrets/<name> (mode 0400) inside exactly the services that need it. Non-sensitive configuration — domain, database name, usernames — travels as environment variables from srcs/.env. The TLS server key is also a secret; the CA private key stays on the host, because make trust makes browsers trust that CA.

Startup order by real healthchecks

depends_on: condition: service_healthy chains the stack. MariaDB is “healthy” only when the application user can connect over TCP — exactly what WordPress needs. WordPress is healthy when php-fpm accepts FastCGI connections. All checks poll at 500ms during startup (--start-interval), so each layer starts the moment the one below is usable:

[term_window title="docker compose up -d"] [out]✔ Container mariadb Healthy 3.9s ✔ Container wordpress Healthy 6.1s ✔ Container nginx Started 6.3s[/out] [/term_window] [callout type="ok" title="restart policy"]All services run with restart: unless-stopped — kill any PID 1 and the container is back in seconds, yet docker stop still means stop. Chosen over on-failure deliberately: a SIGTERM'd daemon exits cleanly (code 0), which on-failure would never revive.[/callout]
