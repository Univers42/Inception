Zero-friction setup

A fresh clone needs exactly one command. make setup (run automatically) provisions every missing piece and never overwrites existing files: srcs/.env from the template, random passwords into secrets/, the /etc/hosts entry, and the full TLS chain — a local Root CA plus a host-signed server certificate.

Entrypoint good practices

Every container boots through the same disciplined pattern:

  1. Fail fast — set -eu, required env validated, secrets checked non-empty. The WordPress entrypoint refuses any admin username containing “admin”.
  2. Guarded one-time init — MariaDB bootstraps accounts via mariadbd --bootstrap behind a success-marker file; WordPress deploys its staged core and installs itself behind a wp-config.php guard. Interrupted first boots self-heal.
  3. Bounded waits — the DB wait probes with php -r 'mysqli_connect(…)' and gives up after 60s; the restart policy retries. Never tail -f, sleep infinity or while true.
  4. exec as the last line — the daemon becomes PID 1 and receives signals directly.
[callout type="warn" title="init guards"]Changing secrets after first boot does not propagate — values are baked at installation. Re-apply with make clean && make.[/callout]

Security posture

  • Passwords exist only as Docker secrets (files, mode 0400) — never in env vars, images or Git. docker inspect shows nothing sensitive.
  • The CA private key never enters a container; nginx receives only the server cert + key.
  • TLS 1.2/1.3 only, single published port, php-fpm workers run as nobody, images ship no unused clients or tools.
  • Init SQL and PHP receive properly escaped values — password content cannot inject.
